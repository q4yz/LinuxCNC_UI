### Resolution Summary
Added comprehensive `pytest` coverage for the FastAPI-based Temperature module: unit tests for module lifecycle/factory and Pydantic settings validation, plus integration tests for the `/sensors` router that mock the hardware layer via `unittest.mock.patch`. All 53 new tests pass; the broader backend suite is unchanged.

### Files Modified
- `backend/tests/test_temperature_module.py`: Added unit tests for the module lifecycle surface (issue #43 § 1) — `setup()` returns a fresh `TemperatureModule`, two calls return independent instances, `on_load()`/`on_unload()` execute without errors, `get_settings_model()` returns a `TemperatureSettings` instance, `get_router()` returns the routed `APIRouter` with the documented paths.
- `backend/tests/test_temperature_settings.py`: Added unit tests for the `TemperatureSettings` Pydantic model (issue #43 § 2) — defaults match the documented values (`sample_period_ms=500`, `ambient_celsius=25.0`, `unit="celsius"`, default `sensor_colors`), `default_factory` returns isolated dicts, every `Field` boundary validator raises `ValidationError` for out-of-bound values, boundary values are accepted, and the `Literal["celsius", "kelvin"]` type rejects all other strings.
- `backend/tests/test_temperature_router.py` (new): Integration tests for the `/sensors` router (issue #43 § 3) — `GET /sensors` calls `stat.poll()` before reading, returns the `SensorsResponse` schema with plain-dict coercion, tolerates empty `temperatures`, and tolerates missing `temperatures` attribute; `POST /sensors/{name}/target` calls `execute_sync_cmd("set_temperature", 0, name, req.target)` with exact arguments, accepts boundary targets (0.0 and 400.0), rejects out-of-range targets, defaults to `status="success"` when the hardware omits the key, the URL `{name}` wins over the body's `sensor_name`, empty/invalid URL names yield `400`, raised `HTTPException` propagates, and a generic `Exception` surfaces as `500`.

### Architectural Decisions
- **Three files mapped to the three issue sections.** The issue requested `test_module.py`, `test_settings.py`, and `test_router.py`. I aligned the names with the existing `test_temperature_<aspect>.py` convention to fit the project's test directory layout, where every feature already has both module-level and settings-level integration tests. The new file is `test_temperature_router.py`; the new tests are appended to the existing `test_temperature_module.py` and `test_temperature_settings.py` rather than to a new file, so the existing integration tests still run alongside the new unit tests.
- **Mocking strategy.** `unittest.mock.patch` is targeted at `modules.temperature.router.get_machine_stat` and `modules.temperature.router.execute_sync_cmd` because the router imports these symbols into its own namespace at module load — patching at the source `hardware` module would not intercept the local references. Using `MagicMock` keeps the assertions on call arguments and return values explicit.
- **No source changes.** The fix is test-only. The router, settings model, and module class are exercised as-is; the new tests describe the existing contract (issue #43 is "write tests", not "rewrite the module"). The only edits to existing test files are *additive* — every prior test still passes.
- **Boundary coverage.** The issue enumerates validation boundaries (`ge=100`/`le=5000`, `ge=-50.0`/`le=100.0`, `Literal["celsius", "kelvin"]`). I added both "rejects out-of-bound" and "accepts boundary" cases using `pytest.parametrize` so the contract is documented in both directions.
- **Pre-existing `test_jog_watchdog.py` errors are unrelated.** Running the full `tests/` directory surfaces 6 errors in `test_jog_watchdog.py` (a `ModuleNotFoundError: No module named 'backend'` import-path issue). These errors reproduce on the unmodified `main` branch and are not caused by this PR.
